# Visual Agent RL 实验总结：2026-09-17

本文汇总本次对话中已核验的实验、评测、代码修改和已知限制，供后续方案评估使用。训练进度采用对话中最后一次检查的快照，不代表阅读时的实时状态。事实、推测与尚未执行的工作分别说明。

## 1. 当前目标与主要问题

项目使用 Qwen3-VL-8B-Instruct 进行 Visual Agent 多轮工具使用 RL。工具包括：

- `grounding_detect`：GroundingDINO 定位。
- `crop_zoom`：裁剪图片，返回给模型继续观察。

当前主要问题：新 RL 实验的训练 reward 上升，但工具调用逐渐消失，最终三榜成绩尚未超过历史 KL step130。新旧评测协议存在差异，因此暂不能直接认定模型能力退步。

### 新旧评测协议不一致

- 历史step130补测日志确认：最多12次模型调用，每次最多512 tokens。
- 本次是6次×6144 tokens。token上限是每次模型生成的上限，不包含输入，也不是整个样本的累计上限。
- 本次参数是助手沿用了另一份 final-eval 脚本，没有先对齐历史协议，属于配置选择疏漏。
- 历史工具版成绩由“旧成功预测＋失败样本补测”合并得到，不是当前版本代码的全量重跑。
- 用户已同意四份评测结束后，再用12×512全量重评新权重；截至本次对话尚未启动。更改协议后不能只补API failed或复用原预测。

因此，当前可以确认前两份新权重的低分不是残留API failed造成的，但不能据此直接判定训练退步。

## 4. 工具调用退化的已确认数据

按实际 `rollout_trace.tool_calls` 统计，调用率指至少执行一次工具的轨迹比例：

| 窗口 | 16卡调用率 | 64卡调用率 |
|---|---:|---:|
| step1–10 | 95.7% | 94.7% |
| step21–30 | 90.5% | — |
| step31–40 | 57.7% | — |
| step44–53 | — | 49.8% |
| step72–81 | 约0.5% | — |
| step143–152 | 0.045%，8960条仅4条 | — |

补充证据：

- 16卡后期输出中的 `<tool_call>` 也只有4条，因此是模型不选择工具，而不是请求被服务器丢失。
- 记录到的工具执行错误率很低：早期约0.07%–0.08%，64卡后期约0.15%。该统计不等价于检测结果的语义质量。
- 16卡平均reward从早期约0.491升到后期0.651；答案得分从约0.436升到0.613。
- 两个数据来源内部的工具调用率都下降，不只是数据混合比例变化。
- 同题内比较工具与直接回答：16卡step21–30，工具路线平均reward低约0.080；后续部分窗口又略高。没有稳定的工具奖励优势，也不能说工具始终有害。

结论：16卡组工具使用行为已明显退化，64卡组也在下降；尚未证明模型丧失工具能力，也未证明这就是三榜下降的原因。

## 5. 与历史实验相比的主要变化

已核对启动日志与代码：

| 变化 | 历史实验 | 新实验 |
|---|---|---|
| 关系题prompt | 要求分别检测目标和参照物 | 先看图，仅不确定时检测 |
| rollout n | 16 | 8 |
| 数据 | 原关系题数据 | 关系题＋DeepEyesV2 |
| 训练轮数计数 | `len(messages)` | assistant生成次数 |
| 工具观察loss mask | 旧实现 | 修正观察与动作区分 |
| 多模态位置编码 | 旧实现 | 修正追加图片后的处理 |

基础模型、学习率1e-6、KL系数0.001未变。历史日志出现过entropy系数0.001和0，不能断言历史step130全程有entropy奖励。

最直接的候选原因是prompt放松工具要求，配合仅奖励答案正确的目标，使直接回答逐渐占优。rollout减少可能降低探索，但尚未做因果对照。第一批轨迹仍有约95%调用工具，说明不是prompt一改就立即失效，而是训练逐步强化了直接回答策略。

不能简单认为题目太容易：后期答案得分约61%，仍有不少错误。更准确的待验证解释是，数据与奖励没有让工具路线呈现稳定、可学习的额外收益。

轮数口径必须区分：

- 训练端旧12是消息数量，新6是assistant次数，不能说模型生成预算减半；实际预算可能接近，具体取决于初始消息结构。
- 评测端历史与当前一直按模型调用次数计轮，因此评测12与6确实不同。

## 6. 已实施的训练正确性修改

此前已实现：

- 工具返回的观察内容不参与生成loss，assistant生成的工具调用动作仍参与训练。
- 修正多轮工具返回后的相关mask和轮数统计。
- 修正追加裁剪图后的多模态位置编码处理。
- prompt明确最多6个assistant回合，保留最终回答机会。

这些修改可能影响学习过程，但目前没有证据表明其导致工具消失。不应为了恢复调用率直接撤回正确性修复。

另有已识别但未解决的差异：评测最后一轮仍可能执行工具，却没有后续回答机会；训练端则可在轮数耗尽时直接结束。

## 7. Judge与reward的最终决定

当前奖励主体：

```text
0.9 × 答案正确 + 0.1 × 格式正确
```

`tool_used`是统计字段，不直接加分。代码另有可选query penalty，是否启用取决于配置。

最终保留的Judge方案：

- 输出TRUE/FALSE，temperature=0，关闭thinking，最多8 tokens，换行停止。
- 兼容旧 `{"verdict": true/false}`。
- 主API默认请求1次；失败、限流、超时、非法输出后切备用，备用默认最多请求2次。
- 明确FALSE是有效判定，不触发备用。
- 初始化及模型列表查询异常也纳入fallback，不直接让reward batch失败。
- HRBench4K、Vision-OPD用确定性选择题规则，不调用Judge；兼容 `B`、`B.`、`B)` 及带选项文本。
- 记录主备请求、TRUE/FALSE、超时、429、异常、非法返回、fallback及unresolved统计。

用户最终选择：unresolved按答案错误处理，保留格式奖励，正常进入GRPO均值、标准差和更新。格式正确且无其他惩罚时，reward为0.1，而不是整条清零。

中途曾考虑完全排除unresolved并修改actor loss，但用户撤回；该轮actor修改已撤销。最终只修改reward/Judge逻辑，25项测试通过。没有为这些修改主动重启现有训练，不能假设运行中的进程已加载最新代码。

轨迹字段也存在版本差异：抽查的16卡后期JSONL没有 `reward_valid` 字段，64卡JSONL有该字段。解释实验时需以实际运行代码与轨迹为准。

## 8. 历史KL step130直接回答评测

9月13日已有完整Native评测，三榜1791条轨迹均已核验：

- 每条仅一次模型调用。
- 实际工具调用数为0。
- `use_tools=false`，请求不传工具定义，不进入工具执行循环。
- 使用独立的简洁回答prompt，不是原Agent prompt。

因此它同时改变了prompt和工具可用性，不是严格的“相同prompt，只关闭工具”。脚本配置单次生成上限为6144 tokens。

原始XLSX的 `raw_response` 保存了消息和模型回答，轨迹仍可查看；`image_path_list`保存图片路径，轨迹中的图片base64已脱敏。

当时代码优先取 `content`，为空才取 `reasoning_content`，未分别完整保存两者。因此不能据此宣称模型没有推理，也不能保证保存了服务单独返回的reasoning字段。已经检查的示例是 `A. rubber`、`A. 27B` 等简短答案，未对全部输出的显式分析比例做统计。

## 9. 资源利用率与跨卡数续训

### 资源利用率

- 工具GPU平均利用率曾观察到约7%–13%，瞬时可达到100%，主要因只在rollout阶段工作。
- 抽查训练耗时：模型更新约46%，old/ref log probability约33%，rollout约15%。这些是特定窗口的统计，不应当作整个实验的固定比例。
- 已编写ModelArts真实RL短训练资源对照脚本：A为当前配置，B为精简工具副本，C为16卡全部训练＋CPU工具。
- 默认2步预热＋5步测量，各组从同一HF权重重新开始；只完成脚本和本地验证，尚未运行真实资源对照。
- 不能直接把约19 GiB的工具模型叠加到训练卡：此前训练显存峰值曾约66 GiB，存在超出80 GiB的风险。

### 跨卡数续训

- 当前跨训练卡数恢复实现采用HF热启动，可恢复模型权重、数据游标和step，但优化器、调度器、随机状态重置，KL reference也会重设。
- 这些状态并非原理上不能恢复；完整跨拓扑恢复需要优化器分片重分配等实现与验证。
- 即便实现完整状态恢复，跨卡数的随机采样和数值结果仍不保证逐位相同。
- 当前正式实验建议保持训练GPU数与并行配置不变；可以暂停后从完整checkpoint恢复，不要求始终使用同一批物理卡。
